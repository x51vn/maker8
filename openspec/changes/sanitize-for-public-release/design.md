## Context

Maker8 is a private video-render worker that was developed with real credentials and internal infrastructure details committed directly to git. The repo contains:

- **16 Google Cloud service-account JSON files** in `gg-tts-keys/` (14 tracked by git, including a `quarantine-2026-04-13/` subfolder) — each contains a live RSA private key and a `client_email` that can be used to call Google Cloud APIs
- **Agent-tooling state files** in `.playwright-mcp/` (10 files: logs, screenshots, YAML session dumps) tracked in git, containing internal IP/port references
- **Internal docs** in `docs/` that reference the private deployment host `10.113.213.9`, the private container registry `<registry>/<org>`, internal service URLs (`<kafka-ui-host>`, `<api-host>/editor8`), and personal local paths (`/home/<user>/...`)
- **Deploy scripts** (`deploy-direct.sh`, `deploy-production.sh`) that hardcode the deployment host IP, SSH key path, and registry hostname
- **`deployment/server2/`** directory with unrelated internal service config (litellm)

The `.gitignore` already has a `gg-tts-keys/*.json` rule, but the files were committed before that rule was added, so they remain tracked.

The git history is 81 commits deep; the credential files appear in at least commits `e9076fa`, `5ea96ad`, and `9dc75b1`.

## Goals / Non-Goals

**Goals:**

- Eliminate all credential material (private keys, service-account emails) from git history and the working tree
- Revoke all exposed credentials before the rewritten history is published
- Remove agent-tooling state files and internal-only docs from the tracked tree
- Harden `.gitignore` so these categories of files cannot be accidentally committed in the future
- Keep all source code (`src/`, `tests/`, `config/`, `scripts/`) and public-facing docs (`README.md`, `docs/ARCHITECTURE.md`, etc.) fully intact
- Produce a clean, publication-ready repo with a `SECURITY.md` for disclosure guidance

**Non-Goals:**

- Rotating credentials for the live production system (that is an ops task, not a code task — listed as a prerequisite)
- Changing any application behavior or pipeline logic
- Publishing to a specific registry or host (that is a separate ops decision)
- Removing all mentions of `x51` branding from source code (the deploy scripts are internal-use tooling; only embedded secrets and private infra details need removal, not brand names)

## Decisions

### D1: Use `git filter-repo` to rewrite history

**Decision:** Use `git filter-repo --path <path> --invert-paths` to excise the credential paths from every commit.

**Alternatives considered:**
- *BFG Repo Cleaner*: requires Java; `git filter-repo` is the Git-project-recommended successor, is pure Python, faster on small repos, and already available via `pip install git-filter-repo`.
- *`git filter-branch`*: officially deprecated by Git; slow and error-prone.

**Rationale:** `git filter-repo` is the standard tool for this task and has no extra runtime dependencies beyond Python 3.

### D2: Revoke credentials before rewriting history

**Decision:** Document a mandatory pre-step: revoke all 14 SA keys in Google Cloud Console and generate new keys, distributed out-of-band, before pushing the rewritten history.

**Rationale:** Once the repo is public, even a brief window between push and revocation is enough for automated secret-scanner bots to harvest the keys. Revocation must precede publication.

### D3: Remove agent-tooling state via `git rm --cached`, add to `.gitignore`

**Decision:** For `.playwright-mcp/` and `.serena/memories/`, use `git rm -r --cached` to untrack the directory tree without deleting local files, then add glob rules to `.gitignore`.

**Rationale:** These files are ephemeral session state generated by dev tooling (Playwright MCP, Serena). They have no value to repo consumers and contain internal IP/port references. No history rewrite is needed — the data is low-risk (no keys), so removing them from HEAD is sufficient.

### D4: Sanitize deploy scripts rather than delete them

**Decision:** Replace the hardcoded values in `deploy-direct.sh` and `deploy-production.sh` (deployment host IP, SSH key path, registry, compose dir, username) with variables sourced from a `.env.deploy` file, which is gitignored. A `.env.deploy.example` with placeholder values is committed instead.

**Alternatives considered:**
- *Delete scripts entirely*: loses documented operational runbook; callers would have to reconstruct manually.
- *Comment out secrets*: leaves the old values in history if done in a new commit; doesn't help if history is rewritten anyway.

**Rationale:** The scripts are useful operational tooling. Parameterizing them makes them generic and reusable for any deployment target, not just the current one.

### D5: Delete internal-only docs, keep public-facing docs

**Decision:** Remove from the tracked tree the following categories of docs:
- Internal PRDs referencing private editor8 system design (`EDITOR8_UI_KEY_MANAGEMENT_PLAIN_TEXT_DB_PRD_2026-04-10.md`, etc.)
- Agent-skill update notes (`X51_COMMIT_SKILL_UPDATE_*.md`)
- Internal commit reports (`COMMIT_REPORT_*.md`)
- Internal service install guides unrelated to maker8 (`SEARXNG_UBUNTU_INSTALL_GUIDE_2026-04-11.md`, `OPENCLAW_*.md`)
- Investigation guides referencing private hostnames/IPs

Keep: `README.md`, `docs/ARCHITECTURE.md`, `docs/schemas/`, `docs/examples/`, `docs/QUICK_REFERENCE.md`, `docs/TTS_CREDENTIAL_ROTATION.md`, `DROPBOX_SETUP.md`, `docs/maker8-specs.md`.

**Rationale:** The removed docs expose the architecture of a separate private system (editor8) and contain internal hostnames. The kept docs are necessary for open-source consumers to understand and use maker8.

### D6: Add `SECURITY.md`

**Decision:** Add a minimal `SECURITY.md` explaining how to report credential leaks, the key management model, and that credential files must never be committed.

**Rationale:** Standard practice for any open-source repo that involves credentials.

## Risks / Trade-offs

- **History rewrite invalidates all local clones** → Mitigation: communicate to all collaborators before force-pushing; document the required `git clone` workflow after rewrite.
- **`git filter-repo` removes the `gg-tts-keys/` JSON files entirely** — the `quarantine-2026-04-13/` subfolder files and the active files will all vanish from history → Mitigation: confirm new keys are provisioned and working in production before rewriting.
- **`docs/QUICK_REFERENCE.md` contains the private Kafka IP `10.113.213.9`** → Mitigation: replace with a generic placeholder (`<kafka-host>:9094`) in the same commit.
- **deploy scripts reference the private registry** — after parameterization, the `.env.deploy.example` must use obvious placeholders, not real values.

## Migration Plan

1. **Pre-step (ops, out-of-band):** Revoke all 14 Google Cloud SA keys in Cloud Console; provision replacement keys for the production worker via `MAKER8_CREDENTIAL_SOURCE=db` path (no new JSON files needed in the repo)
2. Run `git filter-repo` to excise `gg-tts-keys/` from all commits
3. Untrack and gitignore `.playwright-mcp/`, `.serena/memories/`, `deployment/server2/`
4. Parameterize deploy scripts; commit `.env.deploy.example`
5. Remove internal-only docs; patch `docs/QUICK_REFERENCE.md` IPs
6. Strengthen `.gitignore`; add `SECURITY.md`
7. Verify clean with `git log --all -- "gg-tts-keys/*.json"` (must return empty)
8. Force-push rewritten history: `git push --force-with-lease origin main`
9. Publish repo
